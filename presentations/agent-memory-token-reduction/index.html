Cold-Start Tax — every invocation re-fetches the same context from scratch before it can do anything useful. Redundant Tool Calls — the same questions get answered again and again, paid for in tokens each time. Runaway Costs — token bills scale linearly with users × requests; nothing is ever reused. And it compounds with team size: every engineer's agent independently redoes the same discovery and reasoning. Bridge: the fix isn't a bigger context window — it's smarter memory (next slides).

Data Model · 1 of 2 — A virtual file system

Memory lives in SurrealDB 

-- A single primitive stores notes, docs & folders
DEFINE TABLE file SCHEMAFULL;

DEFINE FIELD filename     ON file TYPE string;
DEFINE FIELD parent       ON file TYPE option<record<file>>;
DEFINE FIELD content_type ON file TYPE string;

-- Content (folders simply leave these empty)
DEFINE FIELD content   ON file TYPE option<string>;
DEFINE FIELD embedding ON file TYPE option<array<float>>;

-- Derived path, computed on read
DEFINE FIELD path ON file COMPUTED (
    ($this.parent.path || '') + '/' + $this.filename
) TYPE string;

-- Indexes → semantic similarity and full-text search
DEFINE INDEX file_vec ON file FIELDS embedding
    HNSW DIMENSION 1536 DIST COSINE;
DEFINE ANALYZER memory TOKENIZERS blank,class
    FILTERS lowercase,snowball(english);
DEFINE INDEX file_fts ON file FIELDS content
    SEARCH ANALYZER memory BM25;

One primitive, three jobs

  • Hierarchy — self-referential parent builds a tree
  • Semantics — embedding + HNSW for recall
  • Lifecycle — timestamps & soft delete built in

Search, two ways

Vector recall finds meaning; BM25 finds exact terms — both over the same rows, one engine.

Multi-model Vector (HNSW) + full-text (BM25) indexes serve files and the graph — semantic recall and keyword search, one database.

Data Model · 2 of 2 — A knowledge graph

Memory lives in SurrealDB 

-- Entities & facts as nodes
DEFINE TABLE entity SCHEMAFULL;
DEFINE TABLE fact   SCHEMAFULL;
DEFINE FIELD content   ON fact TYPE string;
DEFINE FIELD embedding ON fact TYPE option<array<float>>;

-- Typed edges via RELATE
RELATE fact->mentions->entity;
RELATE fact->derived_from->file;   -- links back to Type 1

-- Traverse: every fact about an entity
SELECT <-mentions<-fact FROM entity;

-- Same multi-model indexes apply
DEFINE INDEX fact_vec ON fact FIELDS embedding HNSW …;
DEFINE INDEX fact_fts ON fact FIELDS content SEARCH … BM25;
file fact entity mentions derived_from

Facts mention entities and trace back to the files they came from.

Multi-model The same vector (HNSW) + full-text (BM25) indexes power the graph — traverse edges, then rank by meaning or exact terms.

Challenges

Writing memory is easy. Keeping it useful isn't.

01

Select

What's even worth storing?

02

Stay fresh

Is this fact still true?

03

Consolidate

Merge near-duplicates.

04

Find patterns

Turn memories into insight.

05

Restructure

Reorganize as it grows.

06

Forget

Prune what's dead weight.

Select — storing noise costs tokens and pollutes recall; not everything an agent sees is worth keeping. Stay fresh — facts go stale or get contradicted, so supersede / invalidate them, don't just append. Consolidate — merge overlapping memories into canonical ones. Find patterns — cross-memory synthesis turns raw logs into reusable lessons. Restructure — links and schema should evolve as understanding grows. Forget — expiry and pruning keep recall lean (the file schema's soft-delete already helps). These are open problems — and exactly what we've been working on.
